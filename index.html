Data Structures and Algorithms

My coursework helped me understand that choosing an algorithm involves evaluating its behavior and the tradeoffs it introduces. In CS 370: Current and Emerging Trends in Computer Science, I worked with deep Q-learning through CartPole and a pirate navigation agent. Adjusting training parameters and examining results showed me why a solution needs to be evaluated against its goals.

I applied this reasoning to the trip recommendation feature in my capstone. Budget and travel dates act as required filters, while destination and trip length influence weighted scores. A size-k min-heap retains the strongest requested recommendations instead of sorting every eligible trip. Heap selection takes O(n log k) time and uses O(k) additional heap storage, where n is the number of trips evaluated and k is the number of results requested.

Sorting all eligible trips would have been easier to implement. The heap is useful when customers request a small number of results compared with the number of available trips. Implementing it helped me understand how a data structure should serve the problem being solved. I also learned to distinguish the heap's storage requirements from the memory used elsewhere in the application.

Software Engineering and Databases

In CS 465: Full Stack Development I, I built Travlr Getaways by connecting an Angular interface, an Express REST API, and a MongoDB database. This project helped me understand how software components work together to support a complete application. Troubleshooting required me to follow requests from the interface through the server and database to identify where a problem occurred. That experience prepared me to expand the application during my capstone, where changes needed to work consistently across every layer.

The capstone expanded that application through customer and administrator workflows, reservations, recommendations, and database improvements. Adding a reservation feature required coordinated changes to models, routes, controllers, services, forms, and navigation. This strengthened my understanding of software engineering because I had to consider how a change in one layer affected the others.

The database enhancement helped me think beyond storing and retrieving records. I added validation, a unique trip-code index, an index supporting customer reservation history, and an aggregation report. I also revised the seed script to preserve existing trip IDs. This mattered because reservations reference those IDs. Recreating trips could leave reservations pointing to records that no longer existed.

These changes taught me to consider existing data when updating a system. A schema change needs to account for both future input and records already stored in the database.

Security and Testing

In CS 230: Operating Platforms, I worked with authentication and roles in a REST application. That experience provided a foundation for examining access controls in Travlr. During the capstone, I developed a clearer understanding of the difference between authentication and authorization. A valid token identifies a user, but the server still needs to determine whether that user can perform a particular action.

I added server-side role checks and reservation ownership restrictions. Public registration assigns the customer role, and customers can access only their own reservations. Angular route guards and conditional controls present the appropriate interface, while the API enforces permissions on requests.

I also considered how invalid input and database operations could affect the application. Recommendation requests are validated, the reservation summary is restricted to administrators, and the report excludes customer identities. The API blocks deletion of trips with reservations to protect related records. These improvements demonstrate my growing security mindset while also showing that application safeguards have limits, especially when someone changes data directly in the database.

Software Design and Engineering

The first enhancement expanded the application’s trip management features by separating customer and administrator permissions and adding a reservation workflow.

Customers can reserve trips, view their own reservations, and cancel them. Administrators can manage trips and reservation statuses. I connected these workflows through Angular pages, Express routes, authorization middleware, and MongoDB models. The server checks user roles and reservation ownership before allowing access.

I tested authentication failures, role restrictions, and reservation workflows using Postman and the browser. The Angular application built successfully, and all 17 Angular tests passed at this stage.

This work helped me understand the different responsibilities of the interface and the API. Hiding administrator controls makes the page appropriate for customers, but server-side authorization protects against requests sent directly to the API.

Algorithms and Data Structures

The second enhancement added personalized trip recommendations to help customers compare available trips.

The feature considers destination, maximum budget, travel dates, preferred trip length, and the number of results requested. Budget and dates act as required filters. Eligible trips receive weighted scores, and a size-k min-heap retains the strongest matches. The results appear as ranked cards with match percentages and explanations.

Choosing a min-heap gave me a practical way to evaluate algorithmic tradeoffs. Rather than sorting every eligible trip, the algorithm keeps only the requested number of recommendations. I also converted prices and trip lengths from strings into numeric values so they could be compared consistently.

Seven backend recommendation tests and nineteen Angular tests passed after this enhancement. Testing covered exact and partial matches, tied scores, invalid input, reversed dates, and empty results.

The main lesson was that recommendation rules require judgment. Separating required conditions from preferences helped me build results that were useful to customers. This enhancement demonstrates algorithm design, full-stack integration, clear communication, and input validation.

Databases

The third enhancement improved the trip and reservation data supporting the application. I added stronger schema validation, purposeful indexes, and an administrator reservation summary.

Trip codes now have a unique index, and reservations require a whole number of travelers. Trip prices must represent positive amounts with no more than two decimal places. An index on reservation ownership and creation date supports listing a customer's reservations from newest to oldest.

The administrator-only summary uses a MongoDB aggregation pipeline to group reservations by trip and status, count bookings and travelers, and include each trip's name and code. The report does not return customer identities.

I also changed the seed script to preserve existing trip records and their IDs. The API checks for reservations before deleting a trip and returns 409 Conflict when reservations exist.

Testing confirmed that duplicate trip codes were rejected, existing trips passed validation, and the stored reservations had valid user and trip references. These changes taught me to consider existing records and relationships when modifying database rules.
